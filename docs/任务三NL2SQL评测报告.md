# 任务三 NL2SQL 评测报告

## 先说结论

任务三的目标不是让模型“看起来会写 SQL”，而是让自然语言问题最终得到可执行、可复核的数据结果。当前方案在 40 道开发题上达到 95.0%，超过 85% 目标；在 93 道预留测试题上，方案分析前的**设计基线**为 61.3%，按失败题型完成修正后的**回归复核**为 95.7%。

需要明确的是：回归复核使用过设计基线暴露的失败题型，因此它证明的是“修正是否覆盖已发现的问题”，不是一套全新未知测试集上的独立泛化成绩。下一步应新建或重新抽取一套未参与分析的测试题，作为最终泛化验证。

## 面向答辩的汇报叙事

可以按下面四句话讲清楚任务三：

1. **问题是什么**：医疗问题不只是在查一条事实，还经常要求筛选、计数、分组、排序、关联和对比；只让模型自由生成 SQL，结果容易“能运行但答非所问”。
2. **我们怎么解决**：先把问题拆成疾病实体、分析意图和聚合方式；高频问题走确定性语义模板，长尾问题再由模型根据受限 Schema 生成查询计划。
3. **为什么结果可信**：所有路径最后都落到同一个只读 SQL 执行和结果校验链，知识库负责解释和来源，分析库负责数量、排名和统计，两个证据层不混用。
4. **怎样证明有效**：用真实分析数据库构造 133 道题，保存 Gold SQL 和真实执行结果，评测只比较结果是否一致，并把设计基线、方案验证和回归复核分开报告。

## 架构与创新设计

### 1. 先识别分析意图，再决定生成方式

系统不是把整句问题直接丢给模型，而是先识别疾病实体、查询对象、筛选条件、聚合函数、排序方向和 Top-K 等信息。这样做的价值是把“语言理解错误”和“SQL 书写错误”分开，便于定位和修正。

### 2. 确定性路径与开放路径协同

- 高频医疗问法使用项目内确定性模板，保证常见查询的稳定性和可复现性；
- 长尾表达交给模型，但模型只能在当前 Schema 和查询约束内提出 SQL；
- 两条路径汇合到同一个安全执行器，不为模板单独开一套结果口径。

这项设计同时解决了两个矛盾：完全依赖模板会覆盖不足，完全依赖自由生成又会带来波动。

### 3. “双证据分层”让知识库和分析库各司其职

Nexent 绑定的 `ccf_medical_kb` 适合回答“这是什么、为什么、依据来自哪里”；`task3_analytics.db` 适合回答“有多少、排第几、满足哪些条件、如何对比”。因此：

- 疾病定义、病因、症状解释和来源引用由知识库提供；
- 计数、排名、筛选、关联和图表数据由分析库提供；
- 不把向量检索到的文本直接当成统计结果，也不让 SQL 结果替代医学原文依据。

这使任务三既能给出数据洞察，也能在需要解释时回到医学背景和来源证据。

### 4. 安全控制是执行链的一部分

生成的 SQL 需要经过只读语法和对象校验，并在数据库只读模式下执行，同时受查询行数、超时和单次查询数量限制。安全性不依赖模型“自觉遵守提示”，而是由执行边界保证。

### 5. 一次分析形成完整证据链

原始问题、查询计划、SQL、结果数据、图表配置和导出文件由同一个分析记录关联。这样展示的不只是一个答案，还能说明“问题如何被理解、数据如何被计算、图表依据是什么”。

## 评测设计

### 数据和指标

- 开发集：40 道，用于方案设计与迭代；
- 预留测试集：93 道，用于先建立设计基线，再进行回归复核；
- 总计：133 道，覆盖 7 类题型；
- 数据库：固定版本的 `task3_analytics.db`，15 张表、5 个视图；
- 主指标：保留重复行的执行结果一致率；
- 达标线：执行准确率 ≥ 85%。

每道题都有自然语言问题、Gold SQL 和 Gold Result。评测在真实数据库上执行系统生成的 SQL，只比较返回结果，不要求 SQL 字符串与 Gold SQL 一模一样。

### 阶段结果

| 评测阶段 | 答对/总数 | 执行准确率 | 结果性质 | 是否达到 85% |
|---|---:|---:|---|---:|
| 开发集基准 | 25/40 | 62.5% | 方案调整前的能力基准 | 否 |
| 开发集方案验证 | 38/40 | 95.0% | 完成语义路由与模型兜底后的开发集验证 | 是 |
| 测试集设计基线 | 57/93 | 61.3% | 方案分析前的首次测量 | 否 |
| 测试集回归复核 | 89/93 | 95.7% | 针对已发现题型问题的覆盖复核，非独立盲测 | 是 |

### 题型结果

| 题型 | 题数 | 设计基线 | 回归复核 |
|---|---:|---:|---:|
| 单表筛选 | 17 | 100.0% | 100.0% |
| 聚合统计 | 17 | 58.8% | 100.0% |
| 分组统计 | 14 | 64.3% | 100.0% |
| 多条件查询 | 13 | 53.8% | 100.0% |
| Top-K 排序 | 12 | 83.3% | 100.0% |
| 多表联查 | 9 | 11.1% | 100.0% |
| 复杂综合 | 11 | 27.3% | 63.6% |

结果说明：改造收益主要来自聚合、分组、多条件和多表联查等结构化查询能力的补齐；复杂综合仍有 4 道题未匹配，是下一轮独立测试集最需要关注的风险。

## 局限与下一步

当前 95.7% 是回归复核结果，不能替代独立泛化结论；知识库的召回、引用和解释质量也没有计入 NL2SQL 执行准确率。后续应：

1. 新建一套未参与失败分析的测试题，保持数据库版本和评测脚本不变；
2. 对复杂综合题增加三表联查、CTE、子查询和比例计算的独立样本；
3. 为 `ccf_medical_kb` 单独建立召回准确率、引用完整性和解释一致性评测。
