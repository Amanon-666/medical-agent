# MediFlow 工程改进与测试建设计划

## 1. 依据与执行边界

本计划以提交 `26cd331` 的源码为主要依据，并使用当前运行实例的只读接口核对服务状态、数据规模和实际返回结构。既有方案、审稿记录和开发日志只作为检索线索；凡是无法由源码、运行结果或可执行测试相互印证的内容，不作为现状结论。

后续功能改动继续遵守“运行态先验证、提交态再整理”的顺序。每项改动单独形成可部署、可回滚的最小变更；验证通过后再同步源码、测试、部署资产和文档。

## 2. 当前作品的实际能力与价值

| 范围 | 当前可以完成的工作 | 实际价值 | 使用边界 |
| --- | --- | --- | --- |
| 任务一 | 识别 TXT、CSV、JSON、JSONL 和 PDF，按格式选择处理链，调用 DataMate 执行并登记结果数据集 | 保留原有结构处理多格式资料，并把来源、任务状态和结果标识交给后续环节 | PDF 转为 TXT 后进入文本链；处理计划主要由格式决定 |
| 任务二 | 读取任务一结果，解析混合格式记录，抽取和校验医疗实体关系，将有效三元组写入图谱并刷新分析表 | 把新资料增量接入可查询的医学知识库，并保留数据集、文件和来源信息 | 主流程直接调用统一抽取服务，三个 DataMate 抽取算子还没有组成真正的前后级流水线 |
| 任务三 | 执行疾病事实、关系、统计和只读 SQL 查询，生成图表、CSV、HTML 和审计文件 | 把图谱转为可核对的查询和成果文件，适合知识检索、数据核查和分析演示 | Nexent 查询工具与工作台完整分析服务是两条实现路径，结果契约仍需统一 |
| 工程交付 | 已有 MCP 服务、三个智能体配置、在线工作台、部署脚本和运行数据库 | 已形成可以演示三项任务衔接的端到端工程原型 | 空白环境部署、完整评测、许可证和公开接口脱敏仍需正式化 |

作品最适合定位为“医疗数据工程、知识组织与分析原型”。它能够处理公开医学资料和经过合规处理的业务知识数据，支持来源核对、知识更新和分析导出。当前数据结构不包含患者级临床过程，产品文案和演示问题应聚焦知识条目、来源贡献、疾病关系和知识覆盖，避免延伸到患者趋势或临床决策。

## 3. 当前叙事和实现中需要收敛的方向

### 3.1 大图谱规模不能代替智能体效果

运行库的大部分三元组来自公开结构化医学资源，增量流程贡献的数量较小。后续页面和答辩应同时展示“基础知识图谱规模”和“本轮数据新增结果”，重点呈现某个 DataMate 数据集经过三项任务后增加了哪些实体、关系、来源和分析成果。

### 3.2 三个抽取算子需要形成真实流水线

当前任务二主流程在 MCP 服务内调用统一抽取函数；三个 DataMate 算子又各自从原始文本重复执行抽取。正式方案应让实体阶段输出成为关系阶段输入，关系阶段输出成为三元组校验输入，并给每一阶段分配运行标识和可追溯产物。

### 3.3 任务三应统一正式入口

工作台调用 `MedicalAnalysisService`，Nexent 仍主要调用旧查询工具，浏览器在结构化结果不足时会执行本地回退。最有成效的短期调整是把完整分析服务注册为正式 MCP 工具，使 Nexent、MCP 和工作台返回同一分析对象。

### 3.4 后续投入应优先补工程证据

继续扩展封面样式、单个 PDF 场景或静态大屏，对赛题核心说服力的提升有限。近期投入应集中在统一任务三、真实评测、任务二分阶段处理、跨任务血缘和空白环境部署。完成这些工作后，报告中的测试结果、性能分析和端到端价值才有可重复证据。

1. **规则通用化**：把演示专用噪声放入测试样本，增加否定词、药名、剂量、诊断和检查值保护；不再依赖页面隐藏规则处理源头质量问题。

4. **正式性能分析**：评测脚本执行 3 次预热和 10 次正式测量，报告中位数、P95、吞吐量、失败率、CPU 和内存峰值；MinerU 和模型服务耗时单独列示。
5. **验收型工作台**：首页突出本轮运行状态、来源增量、处理质量、可追溯事实和分析成果，弱化单纯的大数字和内部维护入口。

## 5. 正式测试方案

### 5.1 任务一

| 数据包 | 内容 | 主要检查 |
| --- | --- | --- |
| small | TXT、CSV、JSON、JSONL 小样本 | 格式路由、结构保持、字段保持、血缘 |
| pdf | 文本型、扫描型、异常和超限 PDF | 解析状态、TXT 产物、超时和失败返回 |
| standard | 至少 100 条记录 | 质量指标、端到端处理和阶段耗时 |
| scale | 至少 1,000 条记录 | 异步状态、重启恢复、吞吐和资源峰值 |
| mixed | 五种格式混合、空文件、未知扩展 | 分组执行、部分失败、结果登记和原因 |

每个规模先预热 3 次，再测量 10 次。保存文件数、记录数、输入输出 SHA256、结构保持率、医学关键片段保留率、中位数、P95、吞吐和失败率。

### 5.2 任务二

数据集：

- 固定哈希的 CMeEE 开发集；
- 固定哈希的 CMeIE 子集或开发集；
- 100 条由人工复核的项目三元组；
- 任务一输出的五格式混合数据集。

比较离线、模型增强和混合三种抽取方式。计算实体微平均 P/R/F1、关系与严格三元组 P/R/F1、人工准确率、正式入库接受与拒绝、重复数、来源完整率、降级次数和各阶段耗时。

工程门槛固定为：来源完整率 100%、关系头尾实体有效率 100%、故障回滚成功率 100%、相同输入重复新增为零。模型质量门槛在第一次盲测后冻结，冻结后不再根据测试集调整规则。

### 5.3 任务三

建立至少 120 个独立问题：

- 30 个疾病事实；
- 20 个反向关系；
- 20 个聚合与排名；
- 20 个复合条件；
- 15 个来源与图谱关联；
- 15 个危险或数据结构不支持的问题。

标准答案以结果集合为主，不要求 SQL 字符串完全相同。总执行准确率目标不低于赛题要求的 85%，主要类别准确率不低于 75%，执行成功率不低于 95%，危险查询阻断率和三入口一致率均为 100%。原有固定问题只用于回归，不代替独立测试集。

### 5.4 端到端、性能与部署

1. 使用一个冻结的公开数据包连续执行三轮任务一、任务二和任务三。
2. 保存完整标识链、Agent 事件、查询结果和成果包哈希。
3. 性能测试每个规模预热 3 次、正式测量 10 次，不由单次耗时推导并发能力。
4. 部署测试包括一次空白环境安装、一次幂等重跑和一次回滚。

端到端验收要求三轮均成功，跨任务标识完整，增量计数与数据库一致，导出文件可打开且哈希稳定。

## 6. 项目负责人需要提供或确认的内容

1. 冻结用于评测的提交号，并授权一个隔离运行态评测窗口。
2. 确认正式演示数据、外部知识图谱和 CBLUE 数据的来源、许可和可公开范围。
3. 复核由工具预生成的任务二 100 条三元组和任务三 120 个问题标准答案；负责人只需裁决有争议样本。
4. 确认团队真实分工。技术报告当前采用“核心开发者负责主要实现，其他成员参与调研、复核和材料准备”的概括，正式提交前应由负责人确认。
5. 确定 MediFlow 许可证和最终公开代码仓地址。
6. 为干净部署提供一套可重建的隔离 Nexent 与 DataMate 环境，或授权短时创建隔离实例。

## 7. 推荐执行顺序

```text
公开接口脱敏与许可证
  → 统一任务三正式链路
  → 建立可复现评测
  → 重构任务二三阶段算子链
  → 增强任务一计划与状态
  → 修正空白环境部署
  → 增加跨任务增量分析
  → 通用性、性能和页面优化
```

若比赛周期紧，优先完成前四项。它们直接决定作品能否形成可信的端到端方案、可核对的测试结果和可公开的工程交付。
