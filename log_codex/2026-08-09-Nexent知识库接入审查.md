日期：2026-08-09

- 对照赛题“基于 DataMate 和 Nexent”的原意，判断原生知识库是否有必要接入，以及应接入哪些任务。
- 先完成证据审查，不修改业务代码、Agent 运行态、数据库、容器或知识库内容。

## 已确认事实

### 1. 当前三个 Agent 发布配置没有绑定 Nexent 原生知识库工具

`scripts/update_nexent_agents.py` 的工具发现列表没有 `knowledge_base_search`；任务一、任务二、任务三的目标工具集合也均未包含该工具。发布时脚本通过 `enabled_tool_ids` 覆盖 Agent 工具集合，因此未列入目标集合的旧工具会被禁用。当前项目实际使用的是项目自定义 MCP 工具，不是 Nexent 原生知识库检索。

### 2. 项目客户端能管理知识库，但没有完成 Agent 绑定和检索配置

`clients/nexent_client.py` 目前支持列出、创建和导入知识库，但没有更新 Agent 工具实例参数的接口，也没有原生知识库检索封装。`get_es_index_name()` 对已存在知识库最终返回 `None`，不能作为稳定的知识库索引解析方案。

### 3. Nexent 的正确使用方式是“知识库 + Agent 工具实例”两步

官方文档明确要求：创建知识库并上传文档后，在 Agent 配置中启用 `knowledge_base_search`，再选择关联知识库。该工具使用 `query` 和 `index_names` 检索本地知识库，并支持混合、语义和文本检索模式；创建知识库本身不会自动注入所有 Agent。

### 4. Nexent 原生知识库与 DataMate 知识库是两条不同的检索路径

- 截图中来源为 `nexent` 的知识库属于 Nexent 原生本地知识库，应使用 `knowledge_base_search`。
- DataMate 知识库应使用 Nexent 的 `datamate_search`，配置 DataMate 服务地址和知识库索引。
- MediFlow 当前任务一仍以 DataMate 数据集与算子为事实来源，不能把两者混称为同一个知识库能力。

### 5. 任务三网关目前不会把知识库证据传到可视化结果

`demo/task3_interactive_demo/agent_gateway.py` 的工具名白名单没有 `knowledge_base_search`，事件汇总只提取结构化分析结果和工具名称。即使仅在 Nexent UI 中手工启用知识库，当前网关也不会稳定保存检索片段、文档标题、来源路径和分数，任务三页面仍可能只展示 SQLite 分析结果。

### 6. 当前知识库不能直接混合绑定

截图中的 `ccf_medical_kb` 和 `medical_disease_v2` 使用不同向量模型。Nexent 当前 Agent 工具构建逻辑按配置索引取得嵌入模型，并且官方文档要求使用知识库对应的向量模型。未经运行态验证，不应把两个不同嵌入模型的知识库放进同一个检索工具实例。

## 对赛题原意的判断

- 原生知识库不是赛题文字中单独列出的硬性条目；赛题硬性要求是基于 Nexent 构建 Agent，理解任务、规划并调用 DataMate/MCP 能力，以及完成任务二问答和任务三分析。
- 但当前只把 Nexent 当作 MCP 工具编排入口，完全没有使用其已创建的私有知识检索能力，会削弱“Nexent 集成深度”、医学问答的证据性和平台能力展示。
- 因此，用户关于“知识库没有真正用上”的判断成立；建议接入，但不应把知识库检索替换为任务二入库链或任务三统计 SQL。

## 建议的使用边界

### 任务一

暂不把当前疾病知识库强行绑定到任务一。任务一的事实依据是用户数据集、DataMate 算子返回值、质量证据和血缘；现有 `ccf_medical_kb` 是疾病资料库，不是清洗规范库。若后续建立“医疗术语与清洗规范”知识库，再为任务一增加受限的规范查询场景。

### 任务二

可绑定 `ccf_medical_kb`，用于疾病背景、关系类型解释、低可靠候选的医学语境补充和问答证据。实体/关系/三元组生成、校验和入库仍必须以项目 MCP 抽取链和 DataMate 清洗产物为准，不能用向量检索结果替代结构化抽取证据。

### 任务三

这是最适合优先接入的 Agent。疾病详情和医学解释类问题可使用 `knowledge_base_search` 提供文档片段与引用；统计、排行、数量、来源清单、趋势和图表数据仍只使用知识图谱/分析库的结构化工具。任务三应把两类证据分开呈现：知识库负责“文档事实与出处”，SQL/图谱负责“可计算结果”。

## 推荐的最小可部署改动单元（待用户确认）

1. 运行态只读核对：读取 `knowledge_base_search` 工具 ID、三个 Agent 当前版本与工具实例、`ccf_medical_kb` 内部索引名、权限和嵌入模型；不修改数据。
2. 备份任务二/任务三 Agent 当前版本和工具实例配置。
3. 在 `clients/` 增加 Nexent 原生知识库索引解析与工具实例配置适配；在 `scripts/update_nexent_agents.py` 中将知识库名称做成显式配置，不硬编码内部索引 ID。
4. 首期只为任务二、任务三绑定 `knowledge_base_search` 和 `ccf_medical_kb`，并更新提示词路由规则。
5. 扩展任务三事件网关，保存知识库检索证据的标题、来源、分数和片段摘要；没有检索证据时不得声称使用了知识库。
6. 通过真实 Nexent 对话验证工具调用事件、返回证据和页面展示，再同步测试分支；失败时回退到原 Agent 版本并禁用新增工具实例。

## 未确认项与风险

- 尚未读取线上当前 Agent 工具实例和知识库内部索引的实时 API 返回，不能把截图直接当作运行态绑定证据。
- Nexent 官方 `main` 与线上部署版本可能不同；工具更新接口、知识库列表字段和权限行为必须以线上版本实测为准。
- `medical_disease_v2` 是否属于本项目、是否允许作为正式证据源，尚未确认；在确认前不纳入 Agent 配置。
- `ccf_medical_kb` 只有 126 个分块，是否能覆盖任务二/任务三代表性问句，需要用固定查询集做召回和引用质量测试。

## 结论

仅按当时静态发布脚本判断，项目没有显式配置 Nexent 原生知识库；后续运行态核查对这一结论作了更正，详见下节。接入方向仍是把 `ccf_medical_kb` 作为任务二/任务三的文档证据层，同时保留 DataMate、知识图谱和分析库的结构化事实边界；不把疾病知识库硬塞进任务一。
