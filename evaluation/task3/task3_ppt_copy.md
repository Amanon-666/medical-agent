# 任务三 PPT 展示文案

## 这套 PPT 要让评委记住什么

**任务三不是把一句中文机械翻译成 SQL，而是把问题拆成可执行的分析计划，再用真实数据和来源证据把答案交付出来。**

建议叙事顺序：问题难点 → 双证据架构 → 核心创新 → 安全执行 → 评测证据 → 价值与边界。

---

## 第 1 页：任务三解决的不是“会不会写 SQL”

### 页面标题

**让自然语言问题变成可验证的数据洞察**

### 页面正文

用户问：

> “哪些疾病同时包含咳嗽和 X 线检查？关联数量最多的是哪些？”

系统完成四件事：

```text
理解问题 → 识别医学实体与分析意图 → 生成受控查询 → 返回结果与依据
```

### 页面结论

**答案不是模型的一句话，而是由“问题—计划—SQL—结果—图表”串起来的一条证据链。**

### 口播

医疗分析问题往往同时包含实体识别、条件筛选、关联、统计和排序。真正困难的不是让模型生成一段看起来像 SQL 的文字，而是确保它理解了问题，并且算出的结果可以复核。

---

## 第 2 页：先分清“解释依据”和“统计依据”

### 页面标题

**知识库负责解释，分析库负责计算**

### 页面正文

| 用户想知道什么 | 使用什么 | 返回什么 |
|---|---|---|
| 这是什么、有什么症状、为什么会发生 | Nexent Agent 绑定的 `ccf_medical_kb` | 疾病背景、原文片段、来源依据 |
| 有多少、排第几、满足哪些条件 | `task3_analytics.db` | 数量、排名、筛选结果、对比图表 |

### 核心强调

**双证据分层**：不把知识库检索到的文本直接当统计结果，也不让 SQL 结果替代医学原文解释。

### 口播

知识库擅长回答“为什么”和“依据是什么”，分析库擅长回答“有多少”和“怎么排序”。把两类能力分开，既能发挥知识库的解释价值，也能保证统计结果来自真实数据库执行。

---

## 第 3 页：稳定路径和开放路径协同

### 页面标题

**常见问题走稳定路径，长尾问题保留开放能力**

### 页面正文

```text
自然语言问题
      ↓
医学语义规划：疾病实体 / 查询对象 / 条件 / 聚合 / 排序
      ↓
┌────────────────────┬────────────────────┐
│ 确定性语义模板      │ 受限 Schema 模型兜底 │
│ 高频问法，稳定可复现 │ 长尾问法，扩大覆盖面 │
└────────────────────┴────────────────────┘
      ↓
       汇合到同一个只读 SQL 执行器
```

### 创新文案（可做高亮）

> **不是“模板替代模型”，也不是“模型包打一切”，而是让确定性和开放性各自承担最合适的工作。**

### 口播

完全依赖模板会遇到覆盖不足，完全依赖自由生成又容易产生波动。我们先用语义层识别问题类型，常见问题走稳定模板，长尾表达再交给模型；两条路径最后使用同一套安全执行和评测口径。

---

## 第 4 页：安全不是提示词，而是执行边界

### 页面标题

**模型可以提出查询，但不能直接修改数据**

### 页面正文

```text
模型生成 SQL
      ↓
语法校验：只允许单条 SELECT / WITH
      ↓
对象校验：表和字段必须在允许范围内
      ↓
连接隔离：数据库只读模式执行
      ↓
资源限制：行数、超时、单次查询数量受控
      ↓
返回可追溯结果
```

### 创新文案（可做高亮）

> **安全控制不依赖模型“记住规则”，而是把规则落实到 SQL 校验、连接模式和资源限制三个执行边界。**

### 口播

即使模型生成了不合适的语句，查询也必须通过语法、对象和连接层校验。数据库以只读方式打开，安全性由执行环境兜底，而不是只靠一段提示词。

### 页面标题

**评测先记录系统起点，再验证方案是否覆盖问题**

### 页面正文

|---|---:|---:|---|
| 开发集基准 | 25/40 | 62.5% | 方案调整前的能力基准 |

| 测试集设计基线 | 57/93 | 61.3% | 预留测试题在方案分析前的首次测量 |
| 测试集回归复核 | 89/93 | 95.7% | 已知失败题型修正后的覆盖复核 |

**目标线：85%**

- 分题型图：`evaluation/task3/figures/task3_nl2sql_accuracy_by_type_zh.png`。

### 口播

这里使用“设计基线”这样的展示语言，表达的是：在方案分析前，先记录系统原始能力。回归复核虽然达到 95.7%，但已经使用过失败题型信息，所以我们把它定位为修正覆盖证据，不包装成独立盲测成绩。这个口径更清楚，也更容易复现。

### 图表旁的补充说明

**133 道题、7 类题型、真实数据库执行、结果一致率评测。**

## 第 6 页：一次分析，四种可交付结果

### 页面标题

**从一个问题出发，交付答案、数据、图表和依据**

### 页面正文

```text
原始问题
   ↓
analysis_id：串联问题、计划、SQL、结果和图表配置
   ↓
文字回答   结果表格   可视化图表   CSV/JSON/HTML 导出
```

### 页面结论

**同一个分析对象驱动多种输出，用户看到的不只是结论，还能回到结论所依据的数据和来源。**

### 收束口播

任务三的创新不在于单点地让模型写出 SQL，而在于把医学语义、知识库解释、结构化统计、安全执行和结果交付连成一个闭环。当前回归复核已超过 85% 目标；下一步用全新的未知题集验证真正的泛化能力，并为知识库补充独立的召回和引用评测。

## 答辩要点

### 问：任务三和普通 NL2SQL 有什么不同？

答：我们增加了三层约束。第一层是医学语义规划，先理解疾病实体和分析意图；第二层是确定性模板与模型兜底协同，兼顾稳定性和覆盖面；第三层是只读执行和分析记录，把 SQL 结果变成可复核的回答、图表和导出文件。

### 问：为什么不直接让大模型生成 SQL？

答：直接生成会把实体理解、统计逻辑和安全执行混在一起，出错后很难定位。我们先拆解问题，再让模型在受限 Schema 内生成查询，最后统一经过只读执行器。

### 问：为什么知识库不直接负责统计？

答：知识库适合检索疾病背景和来源文本，分析库适合做 JOIN、COUNT、GROUP BY、排序和图表。分层后，统计答案有数据库执行依据，解释答案有知识原文依据。

### 问：95.7% 能不能说成最终测试成绩？

答：不能。它是使用设计基线失败信息后的回归复核，用来证明修正覆盖了已发现问题。最终泛化成绩需要在不参与分析的新测试集上测量。

### 问：85% 是怎么计算的？

答：133 道题每道都有 Gold SQL 和 Gold Result。系统生成的 SQL 在同一真实数据库上执行，结果完全一致才算答对；不要求 SQL 字符串完全相同。
